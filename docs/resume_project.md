# 可用于简历的当前版本

**AI 服饰消费者洞察与运营核查平台｜个人项目**

- 围绕服饰评论分析场景，使用 Python 清洗 10,000 条原始语料，完成文本规范化、指纹去重与冲突排除，保留 9,909 条记录，并隔离 200 条开发集与 100 条独立测试集。
- 搭建并真实运行 Dify 评论分析、经营诊断与策略生成三条工作流，设计情感与多标签问题体系、原文证据校验及失败记录；以 20 条开发样本贯通分析流程，输出 7 类待核查问题。
- 将统计证据转为 5 项经人工批准的核查计划，开发 Streamlit 六个业务页面及人工评估入口，支持工作区隔离、策略版本审核和有效版本 PDF 报告。

以上数字指语料与开发验证规模。尚不能写“准确率达到 XX%”“人工效率提升 XX%”“降低差评率”“提升 GMV”或“已落地到某平台”。AI 辅助开发是事实，面试中应说明本人负责的业务判断、规则选择、审核与实际操作，不能声称手工独立编写全部代码。

## 两分钟讲述

我选择服饰评论这个运营场景，是因为评论中同时存在质量、尺码、描述、履约和售后问题，适合展示如何把非结构化反馈转成运营核查任务。我先处理公开语料，去重并隔离开发集与测试集，不把源情感标签直接当作真值。

随后用 Dify 做了三条实际运行的工作流。第一条逐条提取情感、问题和原文证据；第二条只能引用已有统计事实生成待核查诊断；第三条提出核查计划，经过人工修订与批准才进入报告。我还处理了模型思考文本影响 JSON 解析、证据不匹配和重复调用等问题。

当前 20 条开发评论已贯通整个流程，形成 7 类问题和 5 项已批准核查计划，并做成可上传评论、审核策略和生成报告的本地应用。这里我区分了流程成功与模型正确，也区分了计划批准与实际经营效果。下一步通过人工标注固定测试集评估 F1，并记录相同任务上的实际耗时；在没有订单与商品数据前，不把评论线索说成经营原因或效果。
